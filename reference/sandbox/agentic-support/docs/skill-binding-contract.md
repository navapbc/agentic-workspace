# Skill binding contract

Canonical skills must work when the support tree is shared, relocated, or
installed independently of any one member's folder layout. This contract defines
how they resolve locations.

## Resolution order

Resolve every location independently, in this order:

1. Explicit user or caller binding.
2. Active trusted workspace guidance.
3. The loaded canonical skill's own location, for a resource owned by the support
   tree.
4. Unavailable.

Do not infer a missing workspace lane from a sibling directory, a home directory,
or a prior user's local default. A missing **required** location stops the
affected operation. A missing **optional** location follows the skill's documented
degraded behavior.

## Binding classes

| Class | Resolution | Examples |
| --- | --- | --- |
| Support-owned | Resolve from `AGENTIC_SUPPORT_ROOT`, the directory containing the loaded support tree. | `skills/`, `context-fabric/`, `tools/`, skill-owned `assets/` and `references/`. |
| Workspace-owned | Caller or trusted workspace guidance supplies the location when the workflow needs it. | Product work, prototypes, the checkouts root. |
| User-provided resource | The user supplies the path or identifier for this operation. | A sync manifest, transcript export, or product profile. |

`AGENTIC_WORKSPACE_ROOT` is optional compatibility context, not a source from
which a canonical skill derives other bindings. A skill may use it only after it
has been explicitly supplied or declared by active workspace guidance.

## The workspace descriptor

A machine-local descriptor generated by
`tools/generate-workspace-descriptor.sh` (default
`~/.agentic-workspace/workspace-descriptor.yaml`; consumers and the generator
resolve the location through the `AGENTIC_WORKSPACE_DESCRIPTOR` environment
override, so test fixtures never touch live state) supplies workspace-owned
bindings as an explicit caller source:

- `AGENTIC_REPO_CHECKOUT_ROOT`
- ordered `AGENTIC_WORKING_MATERIALS_ROOT_<n>` entries (the first is the default
  output destination)
- optional `AGENTIC_EXTRA_ROOT_<n>` entries
- `AGENTIC_PRODUCT_WORK_ROOT`, which is role-based: present only when the member
  declared the product-work lane as a working-materials root

**Declared, never derived.** Every machine-local root is declared explicitly by
the member through the setup flow — never inferred from sibling directories or
directory shape. Tools that need a machine-local root resolve it from the
declaration and **fail closed** when it is absent, stale, or invalid: a missing
declaration stops the operation instead of falling back to a guess. Regeneration
must carry forward the full set of previously declared roots; a re-run cannot
silently narrow the declaration. Lanes inside the shared workspace tree are the
scoped exception — they are physical siblings of the support tree and may be
derived from its location.

The file is generated per machine and never synced or committed. Its values are
declarations, not defaults to infer from: a skill still stops when a required lane
is absent from it. The shape is registered at
`context-fabric/schemas/workspace-descriptor/1.0.0/schema.json`.

Why a home-directory file rather than something inside the workspace: the two
consumers have opposite constraints. In-session agents can only rely on files
inside roots the harness exposes; shell scripts can always read a home-directory
file but cannot see the harness's root selection. Each mechanism is designed for
the consumer that can actually reach it.

## Binding tokens in shared documents

Shared documents reference machine-local roots by binding token
(`${AGENTIC_REPO_CHECKOUT_ROOT}/<repo>/`), resolved on each reader's machine
through the descriptor. Binding tokens replace sibling-relative paths, which stop
resolving the moment workspace roots no longer share a common parent.

## Paused skills

A paused, environment-dependent skill must not list a bootstrap script,
selector, or checkout-derived location as a runnable binding. Its pause notice
and failure handling must direct the user to the support-owned resources that do
work, and state plainly that the dependent operation is unavailable.

## Adapter rules

Adapters identify a canonical skill by its stable bundle ID and use the same
resolution order. A harness-specific adapter may provide capability discovery and
a support-root hint, but it must not contain a user-home absolute fallback or make
that hint a prerequisite. When the canonical skill cannot be located, the adapter
uses the core workflow's documented degraded behavior or asks for an explicit
support root.

## Authoring rules

Each canonical skill lists only the bindings it consumes and cites this contract
for shared resolution policy. Support-owned paths are expressed from
`AGENTIC_SUPPORT_ROOT`; workspace-owned paths are described as explicit inputs,
not local defaults. Bundle-owned files use paths relative to their canonical
bundle. Never publish a user-specific absolute local default in a canonical skill
or adapter — `validation/check-workspace.sh` fails on one.
